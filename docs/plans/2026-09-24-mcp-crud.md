# MCP: full admin CRUD over API keys

Base branch: `feat/message-drafts-audience` (message drafts + `CoopPermissionsService`).
Working branch: `feat/mcp-crud`.

## Goal

An API key can do over MCP what its owner can do in the admin REST API for that coop — no
more. Reads and writes, every domain except the ones excluded below.

## Principles

1. **One code path.** Every MCP tool calls the same service method as the matching REST
   route. No business logic in tool files. If a REST controller holds logic, move it into
   the service first, then call it from both.
2. **Same permission as REST.** Each tool declares the `CoopPermissionKey` of its REST route
   (`@RequirePermission` in the controller). The check is live, per call, via
   `CoopPermissionsService` — never cached on the session.
3. **Same validation as REST.** The zod schema describes the tool to the client. The service
   input is validated with the REST DTO class (`class-transformer` + `class-validator`,
   `whitelist: true, forbidNonWhitelisted: true`), so rules cannot drift.
4. **Same semantics as REST.** "Delete" exists only where REST has a delete. Ledger records
   (registrations, payments, dividends) are cancelled/reversed exactly as REST does it.
5. **Key scope.** `ApiKey.scope`: `READ_ONLY` (default, all existing keys) or `READ_WRITE`.
   Write tools refuse a `READ_ONLY` key.
6. **Read-only subscription.** Write tools refuse when `BillingService.isReadOnly(coopId)`,
   like `SubscriptionGuard`.
7. **PII.** Reads apply the same `canViewPII` masking REST applies. No tool ever returns
   `nationalId`, `giftCode`, password/secret fields, or file system paths.
8. **Audit.** Services that take `(userId, ip, userAgent)` get
   `(ownerUserId, 'mcp', 'mcp-api-key:<apiKeyId>')`.

## Excluded on purpose

Privilege and money-routing surfaces stay UI-only: team (admins, roles, invitations,
permissions), API keys, billing, Ponto connect/disconnect, system admin, external API key.
A key must not mint or widen keys or admins. Also excluded: `audience-sync/*`, kiosk
start/end, convocation send-test. `update_coop_settings` uses
`OmitType(UpdateCoopDto, ['brevoApiKey','graphClientSecret','emailEnabled','pontoEnabled'])`
— those carry secrets or system-admin-only switches. Binary uploads (logo, signature, attachments,
signed minutes) are out for now; bank CSV import takes CSV text.

## Task 0 — Foundation (sol, xhigh)

- Prisma: `enum ApiKeyScope { READ_ONLY READ_WRITE }`, `ApiKey.scope @default(READ_ONLY)`,
  migration.
- `ApiKeysService.create(userId, coopId, name, scope)`; `validate()` returns `scope`;
  `McpAuthStore` carries `scope`. REST create DTO accepts `scope`.
- `apps/api/src/modules/mcp/mcp-toolkit.ts` — injectable `McpToolkit` with **one entry
  point**, so no tool can skip a step:

  ```ts
  run<D, R>(
    opts: { permission?: CoopPermissionKey; write?: boolean;
            pii?: 'shareholder' | 'shareholderList'; dto?: ClassConstructor<D> },
    input: unknown,
    fn: (ctx: McpToolContext, dto: D) => Promise<R>,
  ): Promise<object>
  ```

  Order inside `run`: context → dto → fn → PII mask → normalise → error map.
  - context `{ userId, coopId, apiKeyId, canViewPII, audit: { userId, ip, userAgent } }`.
    `ForbiddenException` with a clear message for: missing permission, READ_ONLY key on a
    write, read-only subscription on a write.
  - dto: `plainToInstance(cls, input, { enableImplicitConversion: true })` (matches
    `main.ts` ValidationPipe) + `validate({ whitelist: true, forbidNonWhitelisted: true })`;
    `BadRequestException` listing constraint messages.
  - PII: reuse `common/utils/mask-pii.ts` exactly as the REST controller does
    (`admin.controller.ts` shareholder routes) when `!canViewPII`.
  - normalise: `Decimal.isDecimal(v)` → number (not `instanceof`), `Date` → ISO string;
    strip `nationalId`, `giftCode`, `filePath`, `keyHash`, `passwordHash` at any depth.
  - error map, caught inside `run` (rekog rethrows any non-`McpError` with its raw
    message): Nest `HttpException` → its message; Prisma `P2025` → not found, `P2002` →
    duplicate, other Prisma → "invalid input"; anything else → "internal error" + log.
- Every zod parameter object uses `.strict()`.
- Where REST has no DTO (`createTransfer` inline type, `@Body('reason')` on reject/cancel/
  meeting-cancel, `@Body('content')` minutes), write the DTO and wire REST to it first,
  in the domain task that needs it.
- Transport: rekog `statelessMode: true` + `enableJsonResponse: true` (auth is per
  request; sessions are unused and leak). GET/DELETE return 405, which the spec allows.
- Test harness: `apps/api/test/mcp.e2e-spec.ts` (or the repo's e2e convention) that boots
  the app, creates a key, and runs `initialize` → `tools/list` → `tools/call`.

## Tasks 2–8 — Domains (luna, high each; one tool file per domain)

Each task: tools named `<verb>_<noun>` (`list_`, `get_`, `create_`, `update_`, `delete_`,
plus domain verbs like `approve_registration`). One spec file per tool file covering
permission denial, READ_ONLY denial, tenant isolation, and the happy path.

| # | Domain | REST source | Permission |
|---|---|---|---|
| 2 | Shareholders, minors, households | `admin.controller` shareholders, `household.controller` | `canManageShareholders` |
| 3 | Registrations, transfers, payments, buy/sell | `admin.controller` registrations/transactions | `canManageTransactions` |
| 4 | Share classes, projects, channels, coop settings (non-binary) | `admin.controller` | `canManageShareClasses`, `canManageProjects`, `canManageSettings` |
| 5 | Bank imports/transactions/matching, dividends | `admin.controller` bank + dividends | `canManageTransactions`, `canManageDividends` |
| 6 | Conversations: list/get/send/schedule/reply | `admin.controller` conversations, messages service | `canManageMessages` |
| 7 | Meetings: CRUD, agenda, proxies, convocation, attendance, votes, minutes | `meetings.controller` | `canManageMeetings` |
| 8 | Reports, documents (metadata + download URL), audit logs, referrals | `admin.controller` reports/documents/audit | `canViewReports`, `canViewShareholderRegister` |

Task 6 reverses the draft-only decision on the base branch: with a `READ_WRITE` key and
`canManageMessages`, a key may send. `READ_ONLY` keys and admins without the permission
still cannot.
